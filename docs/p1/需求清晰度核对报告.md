# 文档功能需求清晰度核对——以「不同词的兼容性」为透镜

> 前提（按你的指示调整）：平台不上网的问题撤下；平台定位 = **后期词典学人机交互的正式平台**，不是投稿演示品；双人标注/α 缓议。
> 本报告只回答一个问题：**两份文档把「换一类词也能用」这件事写清楚了吗？**

---

## 一、总体结论（先说答案）

**文档把「可迁移」当成口号写了很多遍（8 处），但没有一处讲清楚「迁移时到底要准备什么」。**
按正式平台的标准，现在的表述会导致一个真实风险：一个新词类的编者拿到平台后，不知道自己该配什么、配到什么程度才算能跑。具体分三档：

- ✅ **写得清楚的 2 处**（可以直接保留）
- ⚠️ **写了但太笼统的 4 处**（方向对，缺操作细节）
- ❌ **没写、但换词类必然要面对的 5 个问题**（文档完全空白）

---

## 二、逐条核对

### ✅ 写得清楚的（保留即可）

**【清晰-1】「配置与引擎解耦」的总原则 —— 文中 §2.4/§3.3/§3.4**
> 「语义特征、图式槽位的定义保存在外部配置文件，而非硬编码在程序内部」「核心引擎与语义特征、图式定义相互解耦」

这一条作为**架构原则**表述是清楚且正确的，三处口径一致。保留。

**【清晰-2】迁移的成本边界 —— 文中 §8 局限第 3 条**
> 「当迁移至其他语义域、其他词类时，无法直接复用现有参数框架，需要依据对应语义范畴的认知特点重新设计特征集与图式结构」

这是全文唯一一处**诚实说清迁移代价**的地方：特征集和图式结构要重做。这句写得很好，应该升格到 §2.4 或 §3.4 正文，而不是藏在局限节。

### ⚠️ 写了但太笼统的（方向对，缺操作定义）

**【笼统-1】「仅需要更换配套的特征集与图式框架」——文中 §2.4**
「更换」是个动词，但读者不知道这个动词的宾语长什么样：
- 特征集配置 = 几个文件？什么格式？哪些字段必填？
- 图式框架配置 = 图式的「定义 + 证据槽位 + 评分方式」是不是都在配置里？
- **平台现状核查**：本仓库特征列名（P1/M1a/C1…）及其 label/group 是**写死在 `src/category_study.py` 的 Python 常量**（FEATURE_COLUMNS），不是外部配置文件——论文说的「配置驱动」目前只对了一半。换词类时这一条会直接违反文中 §3.3 的主张。

**【笼统-2】「验证配置化跨范畴复用能力」——思路文档流程第 16 步**
「复用能力」的验收标准没写。换到什么范畴、跑通到哪一步（标完？聚完？模板出来？）才算「验证了复用」？思路文档和论文都没说。按正式平台标准，这句话目前只是愿景。

**【笼统-3】「18 项细分特征……既有二分类标签，也包含多分类取值」——文中 §3.1**
特征值域的定义方式没有规范化。对移动动词，特征是「0/1/2 三值」；换到情绪动词、言说动词，特征可能是不对称多值或有序等级。文档没说特征值域是否有类型系统（名义/有序/二元），而这直接决定 Gower 距离的计算分支——这是换词类时第一个会算错的坑。

**【笼统-4】「导出英语语义特征矩阵」——思路文档流程第 11 步**
「矩阵」的 schema 没定义：行=义位、列=特征，但缺一个「特征元数据表」（特征名/类型/值域/是否进聚类/分组）。平台现状 cs_sense_features 长表其实已经有这个能力，但文档把它当「矩阵」一笔带过。

### ❌ 没写、但换词类必然要面对的（文档空白，平台也大多没实现）

**【空白-1】新范畴的「义位准入标准」从哪来？**
移动动词的准入靠「[+运动][+路径]+物理自移」这个操作性定义 + 边界仲裁条款。换到言说动词，「什么算一个言说义位」的标准需要重新研制——**这是整个流水线的第一步，文档对这一步的迁移成本只字未提**。这是五个空白里最重要的一条：词池筛选（216→171）花的心血，在迁移叙事里完全隐形了。

**【空白-2】四图式体系是移动动词专属的，换词类后「图式」的概念骨架要不要换？**
文中 §2.3 把「图式」讲成通用理论（引 Fillmore/Talmy），但实际四图式（方式伴随/源点脱离/终点抵达/互动位移）是 Talmy 运动事件专属。换到情绪动词，「图式」变成什么？文档没有回答「图式层本身也是配置的一部分」。**平台现状核查**：四图式名硬编码在 `src/app.py`（方式伴随×2、源点脱离×2……），同样不是配置。

**【空白-3】「范畴」颗粒度怎么定？**
平台的 categories 表现在只有 1 行（RUN）。新词类进来是「一个词类=一个范畴」（如 SAY），还是「一个词类下再分范畴」（如言说动词分「陈述/询问/命令」）？这决定 cs_lexemes/cs_senses 的组织方式，文档没写。

**【空白-4】语料证据槽位与图式的映射关系是不是配置？**
word sketch 的 27 类语法槽位是通用资源，但「哪个槽位给哪个图式供证据」（P2 论文的图式×槽位映射表）是移动动词特调的。换词类后这张映射表必须重做——它到底是配置文件还是代码？文档没提，平台现状也写死。

**【空白-5】AI 辅助层的提示词是不是配置？**
现在 LLM 初筛的固定提示词内嵌移动动词的判定口诀（「有没有真实物体，在物理空间里移动…」）。换词类后提示词必须重写——文档的「配置驱动」清单里没包括提示词层。按正式平台标准，提示词模板（含判定口诀、边界条款、图式清单）应该和特征集一样进配置。

## 三、平台现状 vs 文档承诺的「配置驱动」差距表

| 文档承诺 | 平台现状 | 差距 |
|---|---|---|
| 特征集在外部配置文件（§3.3） | `FEATURE_COLUMNS` Python 常量硬编码 | ❌ 需外置为 YAML/JSON |
| 图式槽位定义在外部配置（§3.3） | 四图式名+槽位映射写死在代码与灌库脚本 | ❌ 需外置 |
| 特征类型系统（§3.1 隐含） | 无显式类型声明（名义/有序），Gower 计算分支靠约定 | ⚠️ 需在特征元数据里加 type 字段 |
| 提示词配置化 | LLM 提示词硬编码判定口诀 | ❌（文档也漏了） |
| 范畴可扩展（categories 表） | 表结构支持多行，但页面上「四图式」「P/M/C」等全局文案按移动动词写死 | ⚠️ UI 层也需要读配置 |
| 迁移验收标准 | 无 | ❌（文档也没有）——建议定义「换范畴跑通五步=迁移成功」 |

**一句话：文档说「配置驱动」，平台真实状态是「半配置半硬编码」，而文档没写的那一半（提示词、图式、准入标准）恰恰是换词类时最难的部分。**

## 四、给文档的修改建议（按正式平台定位）

### 对论文草稿（Lexikos Project的写作-261104）

1. **§3.3 加一段「配置清单」**，把「配置驱动」落到实处。建议明确列出配置文件至少包含五件套：
   ```
   configs/<category>/
   ├── features.yaml      # 特征集：名称/类型(名义|有序|二元)/值域/是否进聚类/分组
   ├── schemas.yaml       # 图式：定义/证据槽位映射/评分参数
   ├── admission.yaml     # 准入标准：操作性定义/边界仲裁条款
   ├── prompts/           # AI 初筛提示词模板（含判定口诀）
   └── corpus_map.yaml    # 语料槽位 → 图式证据面映射
   ```
   有了这个五件套清单，§2.4 的「更换配置即可迁移」才从口号变成可检验的主张。

2. **§3.4「可迁移性」从「预留接口」改写为「三档成熟度」**，如实分级：
   - 已验证：跨**语言**迁移（汉语侧现汉7 + 跑范畴英汉对齐已跑通）
   - 架构就绪、待验证：跨**范畴**迁移（配置五件套定义清楚后，第二个范畴按清单准备）
   - 设计预留：AI 语义检索、交互式切割（如实保留 §3.4 现有说法）

3. **§8 局限第 3 条升格**：「重新设计特征集与图式结构」这句诚实话，应该出现在 §3.4 正文（作为迁移成本的正式说明），局限节只需保留一句呼应。

### 对思路文档（给师兄讨论-Project的思路）

4. **流程第 16 步「验证配置化跨范畴复用能力」补验收标准**，建议写死为：
   > 「复用验证 = 在第二个范畴上，用五件套配置走完『义位筛选→特征标注→聚类→图式提取→模板实例化』五步且不需要修改引擎代码。」
   有了这句，什么叫「验证了复用」就有客观判据了。

5. **补一条流程步骤**：「制定第二范畴的准入标准与特征集（配套五件套）」——目前流程从第 15 步（模板）直接跳到第 16 步（复用验证），中间缺了「新范畴配置研制」这个必经工序。

### 对平台的后续改造（文档之外，供排期参考）

6. 把 `FEATURE_COLUMNS`、四图式定义、LLM 提示词抽到 `configs/` 目录（对应建议 1 的五件套）；页面全局文案改为读配置。
7. 特征元数据加 `type` 字段（nominal/ordinal/binary），Gower 计算按类型走分支。
8. 迁移验收写成一个脚本：输入范畴代码，自动检查五件套齐全 + 跑通五步。
